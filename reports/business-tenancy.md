## Native channel prerequisite and bounded alternatives

Installed Tauri2.10.2, official source06374a902a50d2bd8b8d85593623ad16ac32325a, `src/webview/mod.rs:1799` exempts `plugin:__TAURI_CHANNEL__|fetch` from ACL. `src/ipc/channel.rs:319–337` removes an ID from the application-wide queue without comparing originating window. `channel_on` at147 supports `Builder::channel_interceptor`, but private `from_callback_fn` at246–282 does not. `src/ipc/protocol.rs:367–407` uses that private producer for eligible **non-macOS/non-iOS** postMessage JSON/raw responses; this does not prove that particular fallback executes on this Mac. Root independently confirmed these exact source paths. No cross-window data theft was executed and no cross-platform runtime proof is claimed.

The interceptor alone cannot certify every producer. Therefore `business_window_context.tenantWindowAvailable=false`; there is no production tenant-window creation endpoint, no global channel transport replacement and no vendor patch. The prepared session/ACL/control code and tests do not advertise a secure native tenant window. Native controls use only injected caller-window operations because the framework's generic window plugin accepts a target label; global event subscription is denied.

Current safe boundary: browser tenant HTTP accounts/settings/tasks plus trusted native platform access. A separately authorized native closure could bind every framework queue item/fetch to its originating webview across both producer paths, with raw/large/end-order/error/cancellation and wrong-window tests; that requires a reviewed upstream or pinned dependency correction and is **not authorized/applied here**. A separate process with no host IPC/queue sharing is a larger alternative, outside this increment. Do not substitute frontend discovery filtering, hidden IPC methods, interceptor-only handling or host-window tenant content for enforcement. Execution isolation and B tenant connection/legacy entrustment remain separate scoped work.
