**What the source verifies**

- **Codeg supplies execution coordination, not organization membership.** The engineering task requires a folder and carries run generation, connection, worktree/branch and merge state. Its claim path uses a conditional update and records run events/actions in the transaction. Preserve that machinery as an optional execution attached to business work. The web boundary authenticates a configured operator token; Ops derives one configured account and a fixed transport actor. These are not individual employee roles. The Desk bridge already derives live ancestry/task/run and a stable agent policy key server-side, then calls accepted domain helpers. [Task model](https://github.com/Adanmohh/codeg/blob/5613962451389b4c50b17b0126ab9e84a9af6b58/src-tauri/src/db/entities/work_task.rs), [claim implementation, lines 777–945](https://github.com/Adanmohh/codeg/blob/5613962451389b4c50b17b0126ab9e84a9af6b58/src-tauri/src/db/service/work_task_service.rs#L777), [web auth](https://github.com/Adanmohh/codeg/blob/5613962451389b4c50b17b0126ab9e84a9af6b58/src-tauri/src/web/auth.rs), [Ops operator](https://github.com/Adanmohh/codeg/blob/5613962451389b4c50b17b0126ab9e84a9af6b58/src-tauri/src/ops/mod.rs), [Desk bridge](https://github.com/Adanmohh/codeg/blob/5613962451389b4c50b17b0126ab9e84a9af6b58/src-tauri/src/work_task/desk.rs).

- **IntroMail is the closer business-domain starting point, with incomplete task authority.** Tasks have lists, creator, optional customer/thread links, hierarchy, due dates and recurrence without requiring git. The inspected Task/schema has no explicit assignee or accountable owner; watchers and favorites are different concepts. Lists/boards distinguish personal ownership from shared access, while BoardPref filters are presentation. HTTP and agent operations reuse task services; the agent pack checks both agent and acting-human visibility. However, HTTP task creation delegates directly to a service whose list check verifies existence, not list ownership. A concrete unexecuted probe is user B creating a task with user A’s private `list_id`. Authorization cannot be inferred from the filtered UI. [Models: TaskList/Task, lines 341–427; BoardPref, 544–568](https://github.com/IntroInnovation/intromail/blob/0bd24dfe284b888aa9f602fa1fd00e337ea38874/backend/app/models.py#L341), [HTTP create, 1119–1134](https://github.com/IntroInnovation/intromail/blob/0bd24dfe284b888aa9f602fa1fd00e337ea38874/backend/app/routers/tasks.py#L1119), [service visibility and create, 43–73 / 215–275](https://github.com/IntroInnovation/intromail/blob/0bd24dfe284b888aa9f602fa1fd00e337ea38874/backend/app/services/task_ops.py#L215), [agent visibility intersection](https://github.com/IntroInnovation/intromail/blob/0bd24dfe284b888aa9f602fa1fd00e337ea38874/backend/app/services/agent/tasks_pack.py#L28).

- **IntroMail’s persisted queue is not evidence of safe distributed execution.** Its dispatcher selects pending rows, processes them, then marks them processed; no claim lease or fencing appears in that path. Completion checks the loaded object before recurrence/notifications, commits, then emits a time-tracking event. Concurrent dispatch/completion and a crash in that post-commit gap require proof; duplicate effects were not reproduced here. MCP authentication does correctly resolve hashed, revocable tokens to an actual human user and supports domain narrowing. Its MCP “tasks” wrap approval proposals and must not be mistaken for business tasks or a durable workflow engine. - **OpenProject demonstrates server-side task permissions separate from assignment.** A work package distinguishes author, assignee and responsible principal. Membership attaches roles to projects/entities, and roles contain permissions. The API filters visible work packages and authorizes access; update contracts separately validate access, edit permission, source-project move permission and lock version. **Five concrete recommendations — proposed architecture, not implemented behavior**

1. **Introduce one central business-task record.** Include organization, title/outcome, business status, accountable human owner (or explicit unassigned queue), human/agent executor, creator, due date, revision and authorized context links. Attach zero or more engineering executions by stable IDs. Marketing, feedback and human work must remain valid without folders, branches or a running agent. Desktops synchronize through the authoritative service; do not synchronize SQLite files.

2. **Enforce resource and action permissions in shared backend operations.** Authenticate individual organization members; model stable agent principals separately. Check organization/team/resource access for reads and every mutation, including creation, moves, assignment and review. Ownership, executor assignment and board filters confer no implicit authority. Derive identities from authenticated sessions/delegations, never caller actor strings. Preserve human destructive approval and exact reviewed revisions.

3. **Treat desktop CLI execution as a separate trust boundary.** Retain live task/run binding, stable policy identity and revocation checks for mediated tools. Scope central capabilities to organization, resource, operation and generation. An arbitrary CLI running with the same local user’s filesystem/network authority is not contained by an MCP allowlist; the current Ops source explicitly disclaims an OS sandbox. Keep provider credentials in trusted backend execution, and do not advertise agent isolation until execution permissions/credential reach are demonstrated.

4. **Start with transactional state plus an outbox and claimed jobs.** Atomically persist the business change, audit event and pending job. Use expected revisions, leases with generation fencing, bounded retries and stable operation IDs; retain unknown-outcome/no-resend handling for external actions. A persisted queue or worker lease does not make external effects exactly once. Add Flowable/Temporal only if concrete long-running coordination requirements outgrow this smaller model.

5. **Prove the boundary before widening features.** Stage A: two users/two desktops, cross-organization/private-list denial, owner-versus-executor permissions, stale revision conflict and revoked membership. Stage B: disconnect/reconnect recovery and two competing workers, crash before/after external acknowledgement, duplicate delivery and cancellation fencing. Stage C: scoped agent read/draft/propose, revoked/stale run denial and rejection of attempted approval/credential access. Use synthetic providers; business tasks must work while every engineering runner is offline.
