# Business AI workspace — root acceptance

This restates the owner's previously agreed product requirements. AI orchestration,
real agent/terminal sessions and role-based business views in one shared workspace
are required delivery, not a newly requested expansion or an optional later phase.
The owner should not need to repeat them during checkpoint coordination.

This is the next delivery priority after the owner's direct observation that the
business preview has no usable AI chat, agents or terminal. It is a plan, not an
implementation or acceptance claim. Existing engine and workspace components are
the reuse baseline; tickets owns the execution contract, rebrand the shared UI,
and approvals the independent authority review. Root remains orchestration-only.

The first user journey is: open a business task, choose an available configured
AI/CLI, work through chat or terminal beside the task, and return a result for
human review. A marketing or feedback user must not need an engineering project
to understand or begin that workflow. Tasks, tables, boards and source review
remain usable alongside the session in the same tabs and panes.

| Gate | Observable result |
| --- | --- |
| Entry and role | A permitted person can start or attach an actually supported existing AI session from the shared workspace/task. Capability and connection state come from backend authority. Labels explain what the session can do; disabled placeholders do not count as delivery. |
| One workspace | Task/data view, chat and terminal occupy real persistent tabs/panes. Changing layout, language or the active tab preserves unsaved human work and the session. No separate engineering-only navigation is needed for the business journey. |
| Real execution | A typed request reaches the existing runner; streaming output, tool activity, completion/failure and cancellation are observable. Reconnection recovers the authorized session without duplicating a launch. Synthetic runner checks and an actual configured-provider run must be reported separately. |
| Shared task outcome | The same human/agent task records identify who requested and performed work. Results can become a proposed deliverable through existing authorization and review operations; transcript/private source content is not automatically published. Human acceptance remains explicit. |
| Tenant authority | Session, run, task, files, events and operation families are bound to the current permitted tenant/member and captured authority. Foreign resources, revoked credentials and stale lifecycle generations are denied. Role names, working directory and hidden tools alone do not establish isolation. |
| CLI and credentials | Reuse configured clients through an explicit authorized execution profile. The contract names credential custody, filesystem/process isolation and session ownership. Tenant sessions cannot inherit host credentials, arbitrary host shell powers or the broad original companion token. No blanket subscription compatibility claim. |
| Existing operator path | Separately identify what the already-authorized original operator can reuse immediately. This may shorten an initial working integration, but it neither impersonates a tenant nor closes tenant execution/native isolation requirements. |
| Verified interface | Playwright CLI tests the real task→AI session→result→review flow, role denials, cancellation/recovery and tabs/panes. Final Design Studio checks cover the integrated experience, with evidence tied to exact source/assets. Native tenant support retains its separate channel boundary. |

The worker contract must name concrete source files and the smallest implementable
slices, each with a runnable synthetic proof and an owner. Reuse the prior tenancy
and companion findings; research only unresolved primitives through installed
source, then pinned gh api sources. Do not introduce a new engine, dependency,
credential migration or live provider action merely to prepare this contract.

New-tenant email/Hafidh host-resource entrustment is secondary to this AI flow.
Content planning/calendar and wider marketing/channel surfaces remain part of the
larger product direction, and are not completed by the current tasks/Sources UI.
